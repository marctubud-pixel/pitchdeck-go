## 0. 一页纸摘要

### 是什么

一个以「比稿项目」为单位的工作台：

```
接单 → 判断 → 情报 → 策略 → 验收 → 交付 → 复盘
```

AI 做案头工作，人做判断。不是聊天 Bot，不是 PPT 生成器。

### 给谁

| 优先级 | 用户 | 场景 |
|---|---|---|
| P0 | 一人公司 / 小团队（你） | 接单、判断、定稿 |
| P1 | 中小广告 / 公关公司合伙人 | 比稿多、缺人手，把前端外包 |
| P2 | 服装 / 时尚品牌市场部 | 上新、大促、季节 campaign |

### 解决什么

比稿的三个浪费：

1. **看不懂 brief**：口头需求、信息缺失、评分标准不明确，导致方向错。
2. **方向错得晚**：写完 60 页才发现客户不想要，返工 20 小时。
3. **经验不沉淀**：赢了不知道为什么赢，输了不复盘，下一单从零开始。

### v0.1 做什么

| 编号 | 功能 | 一句话 |
|---|---|---|
| F1 | 接单卡 | brief → 任务书 + 反问清单 |
| F2 | 启动包 | 论点 / 模块 / 骨架 / 工时 / 风险 / 不确定项 |
| F3 | 策略卡 ×3 | 三个方向，带证据、带预算量级 |
| F4 | 验收官 | 每个阶段 Pass / Fix / Redo + 可执行的修改指令 |
| F5 | 复盘存档 | 复盘卡 + Outcome，字段按将来可检索设计 |

### 5 个功能、6 个闸门

```
接单 → 判断 → 启动包 → 情报 → 策略 → 生产* → 合稿 → 验收 → 交付 → 复盘
  G1     G2      G3               G4              G5        G6
```

\* 生产与合稿在 v0.1 由人工完成，只固定接口。

**G3（启动包确认）是 v0.1 最关键的闸门**：它把「方向错」的成本压在一页纸之内，而不是 60 页之后。

### 不做什么

创意生成、媒介排期、自动出 deck、先例自动检索、多用户权限、计费系统。

### 成功指标

| 指标 | 目标 |
|---|---|
| 交付时间 | 24 小时内 |
| 单项目成本 | < ¥50 |
| 单项目人时 | < 6 小时 |
| 90 天付费客户 | ≥ 2 个 |
| 复购 / 转介绍 | ≥ 50% |

## 1. 背景与假设

### 1.1 问题

一次正式比稿，从拿到 brief 到提报，通常 15–30 人天。其中真正产生差异的是「洞察 + 策略」，但大量时间花在：

- 拆 brief、找资料、做竞品扫描；
- 写 60–80 页 deck、调格式、配图；
- 多团队合稿、对齐口径；
- 答辩前临时补 Q&A。

更贵的是**方向错**：策略没对齐，创意和媒介全废，最后 48 小时推倒重来。

### 1.2 现有方案为什么不够

| 方案 | 强在哪 | 不够在哪 |
|---|---|---|
| 小方同学 | 生成快、模板多、私有化、有分发 | 生成完即止，不掌握输赢；横向太宽，行业浅 |
| 智小虎 | 案例库、评估、ROI 预测 | 偏决策与评估，生成和交付弱 |
| Pitch Box | 流程完整、证据链、评审 rubric | 国内口头 brief 不匹配；知识库冷启动重 |
| 通用 AI | 便宜、灵活 | 不可控、无沉淀、每单从零 |

**空位：把「生成」和「赢」连起来，并且只做一个行业。**

### 1.3 三条假设

| 编号 | 假设 | 如果不成立 |
|---|---|---|
| H1 | 客户愿意为「24 小时出一版能提报的方案」付 ¥3,800+ | 降价或改按结果分成；再不行换切口 |
| H2 | 客户最终要的是 deck，但「先看 3 张策略卡再写 deck」能显著降低返工与中途流失 | 回到「先交一版厚 deck」；策略卡降级为内部产物，不做客户可见 |
| H3 | 输赢数据回流能显著提升第 N 单质量 | 产品退化为生成器，护城河消失，需重新定位 |

### 1.4 怎么验证

- 前 2 单：**手工交付，不写代码**，记录每步人时与客户反应。
- 第 3 单起：用 v0.1 工具，对比人时是否下降 30% 以上。
- 90 天：看「2 个付费 + 1 个复购」是否达成。

## 2. 用户与场景

### 2.1 用户

**P0 · 一人公司（你）**

- 目标：一年 100–300 万营收，净利 200 万上下。
- 现状：有广告行业认知，有服装 / 电商朋友，无跨境资源。
- 关键动作：接单、判断接不接、选方向、定稿、复盘。

**P1 · 中小广告 / 公关公司合伙人**

- 痛点：比稿多、senior 少、熬夜成本高。
- 诉求：把「前端脏活」外包，自己保留客户关系和最终创意。
- 付费意愿：按次或按月，最看重「不丢人、能提报」。

**P2 · 服装 / 时尚品牌市场部**

- 痛点：每季上新都要方案，内部养不起完整策划团队。
- 诉求：快、懂行业、能直接给老板看。
- 付费意愿：走市场费用，比软件预算高。

### 2.2 三个场景

**S1 · 服装品牌秋冬上新比稿（24 小时）**

- 09:00 收到 brief（PDF + 微信语音补充）
- 10:00 任务书 + 5 个反问 → **G1**
- 10:30 判断：Go，报价 ¥6,800 → **G2**
- 11:00 启动包：论点 / 模块（不含媒介）/ 6 章 42 页 / 3 个不确定项 → **G3**
- 12:00 情报：竞品近 90 天动作、小红书人群、平台热点（只查启动包圈定的范围）
- 15:00 三张策略卡 → 客户选 1 个 → **G4**
- 18:00 人工拼 deck（Gamma + 模板）
- 20:00 验收 + Q&A → **G5**
- 次日 09:00 提报
- 次日 18:00 复盘 → **G6**

**S2 · 广告公司临时比稿外包（48 小时）**

- 对方给策略框架，你补洞察、创意方向和 deck。
- 关键：不抢客户关系，只做「后端产能」。
- 交付：策略卡 + deck + 答辩 Q&A，署对方品牌。

**S3 · 甲方内部立项（3–5 天）**

- 输入：老板一句话 + 竞品参考。
- 输出：brief + 3 个方向 + 预算量级，用于内部立项或对外招标。
- 这是「甲方侧」的入口，v0.2 再展开。

### 2.3 非目标用户

- 4A 总部策略部（他们有自己的方法论和知识库）。
- 大型企业（需要 first-party 数据、MMM、CDP）。
- 纯执行型代运营（不需要策略）。

## 3. 产品定义与边界

### 3.1 一句话定义

> **24 小时交付出一个能提报的比稿方案。**

### 3.2 不是什么

| 不是 | 原因 |
|---|---|
| 聊天 Bot | 比稿是项目，不是对话；聊天会让成本失控 |
| PPT 生成器 | 红海，且不解决「赢」的问题 |
| 投放工具 | 不碰广告账户，不承诺 ROI |
| CRM | 不做客户管理，只做项目 |
| 通用 SaaS | 第一年只服务服装 / 时尚 + 电商 |

### 3.3 v0.1 范围

| 功能 | 输入 | 输出 | 谁用 |
|---|---|---|---|
| F1 接单卡 | brief 原文 / 文件 / 语音 / 聊天记录 | 任务书 + 缺口清单 + 反问提纲 | 你 |
| F2 启动包 | 任务书 + 客户历史 | 论点 / 模块 / 骨架 / 工时 / 风险 / 不确定项 / 决策日志 / 置信度 | 你（拍板） |
| F3 策略卡 ×3 | 任务书 + 证据卡 | 3 张一页纸策略卡 | 你 + 客户 |
| F4 验收官 | 任一阶段产物 + 验收清单 | Pass / Fix / Redo + 可执行的修改指令 | 你 |
| F5 复盘存档 | 结果 + 客户反馈 + 评委原话 | 复盘卡 / Outcome / Playbook 更新建议 | 你 |

**F5 在 v0.1 只存不取。** 先例检索是 v0.2 的事，但字段必须按「向量 + 结构化过滤」双路可检索来设计，否则后面要重做。

### 3.4 与竞品差异

| 维度 | 小方同学 | C |
|---|---|---|
| 起点 | 一句 brief | brief + 先例 + 客户历史 |
| 核心产出 | deck | 启动包 + 3 张策略卡 + deck + 自检 |
| 闭环 | 生成完即止 | 赢 / 输回流，进 Playbook |
| 行业 | 横向 | 服装 / 时尚 + 电商 |
| 人的角色 | 工具使用者 | 总导演，拍板 |
| 定价 | 订阅 / 私有化 | 按次 + 月度陪跑 |

### 3.5 成功与失败的定义

**成功（v0.1）**

- 2 个真实项目跑通，单项目人时 < 6h。
- 至少 1 个客户愿意付第二次钱。
- 复盘卡 100% 填写。

**失败（v0.1）**

- 单项目人时 > 10h，且优化不下来。
- 客户反馈「AI 味重、不能用」。
- 90 天没有付费客户。

## 4. 核心流程与闸门

### 4.1 状态机

```
S0 接单 ─▶ S1 判断 ─▶ S2 启动包 ─▶ S3 情报 ─▶ S4 策略 ─▶ S5 生产 ─▶ S6 合稿
  │           │            │                      │         (可选)       │
 G1          G2           G3                     G4                      G5
  │           │            │                      │                      │
  ▼           ▼            ▼                      ▼                      ▼
确认任务书   接不接/报价  确认论点·模块·骨架      选方向                 定稿
                                                                          │
                                              S7 验收 ◀───────────────────┘
                                                 │
                                              S8 交付
                                                 │
                                              S9 复盘 ──▶ G6 ──▶ 档案
```

**为什么启动包在情报之前：** 先由执行总监圈定「查什么、不查什么、要哪几个模块」，再花钱做情报。否则情报员会把预算花在与本次论点无关的方向上。情报回来后若与论点冲突，启动包升到 v2，但**不重新开闸门**，只在决策日志里记一条。

### 4.2 六个闸门

| 闸门 | 位置 | 人的动作 | 不通过怎么办 |
|---|---|---|---|
| G1 | S0 后 | 确认任务书、补反问 | 回 S0，最多 2 轮 |
| G2 | S1 后 | 决定接不接、报多少 | No-Go 则归档，不进入 |
| **G3** | **S2 后** | **确认论点、模块、骨架；看「三个不确定」** | 改字段 / 重来；最多 2 轮 |
| G4 | S4 后 | 选方向、定调 | 回 S4，最多 2 轮 |
| G5 | S6 后 | 定稿、改 3 处 | 回 S6 |
| G6 | S9 后 | 录输赢原因 | 不填则项目不关闭 |

**G3 是 v0.1 最重要的一道闸。** 前面的接单和判断都可以快，但论点、模块、骨架一旦错了，后面所有 Agent 都在放大错误。这一道必须让「不确定项」显性化，而不是让人从 42 页骨架里自己找问题。

**G3 的放行级别**（执行总监自己判断该让看多少）：

| 级别 | 触发条件（满足任一即升级） | 人的动作 |
|---|---|---|
| 自动放行 | 预算 < 20 万；≥2 个相似案例；无合规红线；置信度 ≥ 0.85；人时 < 6h | 扫一眼，点通过 |
| 建议确认 | 预算 20–80 万；只有 1 个案例；置信度 0.6–0.85；跨行业 | 看「三个不确定」并拍板 |
| 必须人工 | 预算 > 80 万；无相似案例；医疗 / 金融 / 政治 / 未成年人；客户有硬性 KPI、代言人、排他；策略与创意冲突 | 亲自主持 G3 |

阈值先按这套设，跑满 10 单后再调。**如果「自动放行」也让人看 40 分钟，这个角色就白设了。**

### 4.3 各状态规格

#### S0 · 接单（Intake）

| 项 | 内容 |
|---|---|
| 输入 | brief 原文、PDF/Word、语音、微信聊天记录、参考图 |
| 输出 | 任务书（目标 / 人群 / 交付物 / 预算 / 排期 / 评分标准）、缺口清单、反问提纲 |
| 负责人 | 接单员 |
| 验收 | 5 项齐全；缺口 ≥ 1；反问 ≤ 8 条；无歧义 |
| 失败 | 信息不足 → 标「待客户确认」，不阻塞，但 G1 必须确认 |
| 预算 | < ¥2 / 次，< 60 秒 |

#### S1 · 判断（Qualify）

| 项 | 内容 |
|---|---|
| 输入 | 任务书 + 客户历史 + 行业 Playbook |
| 输出 | Go / Caution / No-Go + 3 条理由 + 预计人天 + 报价建议 + 赢面 |
| 负责人 | 守门员 + 总导演（G2） |
| 验收 | 结论有 3 条理由；人天误差 < 30%；报价在区间内 |
| 失败 | 信息不足 → 标 Caution，给出「补什么信息能变 Go」 |
| 预算 | < ¥1 / 次，< 30 秒 |

#### S2 · 启动包（Kickoff，执行总监）

| 项 | 内容 |
|---|---|
| 输入 | 任务书 + 客户历史 + 行业 Playbook + 先例卡（v0.2） |
| 输出 | 8 个字段：① 一句话论点 ② 模块清单（含「为什么不要 X」）③ 提案骨架（章 · 页数）④ 工时估算 ⑤ Top 3 风险 ⑥ 三个不确定项 ⑦ 决策日志 ⑧ 置信度 + 放行级别 |
| 负责人 | 执行总监（AI）+ 总导演（G3） |
| 验收 | 8 字段齐全；不确定项 ≥ 2 条；骨架页数与 pitch 类型匹配（服装创意比稿 30–40 页）；模块清单明确写出砍掉了什么及原因；brief 必答项已映射到具体页码 |
| 失败 | schema 不合法 → 重试 1 次 → 仍失败降级纯文本 + 强制人工；不确定项为 0 → 视为失败重跑（说明它在装懂） |
| 预算 | < ¥3 / 次，< 90 秒 |

**启动包的三个反模式**（必须拦）：

1. **不确定项写成「需进一步了解客户需求」**——这是废话，必须是可回答的具体问题（「主推西装还是针织」）。
2. **模块全开**——什么都做等于没做，砍掉的模块必须写理由。
3. **骨架页数超预算还硬塞**——40 页能讲完的写到 80 页，就是没想清楚。

#### S3 · 情报（Research）

| 项 | 内容 |
|---|---|
| 输入 | 启动包圈定的品类、品牌、竞品清单、平台 |
| 输出 | 证据卡 ≥ 10 条，每条含 claim / source_url / source_date / confidence |
| 负责人 | 情报员 |
| 验收 | 来源可点开；无编造；时效 < 90 天（历史资料除外）；**只查启动包圈定的范围** |
| 失败 | 找不到 → 标「待补充」，不编 |
| 预算 | < ¥10 / 次，< 20 分钟 |

#### S4 · 策略（Strategy）

| 项 | 内容 |
|---|---|
| 输入 | 任务书 + 启动包 + 证据卡 + 先例卡（v0.2） |
| 输出 | 3 张策略卡：主张 / 洞察 / 证据 / 场景 / 预算重心 / 风险 |
| 负责人 | 策略 + 总导演（G4） |
| 验收 | 3 个方向互斥；每个能一句话说清；每个有 ≥ 2 条证据；每个有预算量级；**不超出启动包定下的模块边界** |
| 失败 | 方向同质化 → 重跑；证据不足 → 标「待补充」；与启动包论点冲突 → 回 G3 而非自行改方向 |
| 预算 | < ¥8 / 次，< 5 分钟 |

#### S5 · 生产（Produce，v0.1 不做）

v0.1 由人工用 Gamma / PPT 模板完成。
本状态只定义接口：输入选中的策略卡，输出创意资产清单（KV / 脚本 / 文案 / KOL）。
v0.3 再自动化。

#### S6 · 合稿（Compose，v0.1 人工）

| 项 | 内容 |
|---|---|
| 输入 | 策略卡 + 人工创意资产 + 启动包的骨架 |
| 输出 | Deck 初稿 |
| 验收 | 必答项全覆盖；策略—创意一致；页数在启动包预算内（服装创意比稿 30–40 页） |
| 失败 | 不一致 → 回 S4 或 S6；偏离骨架 → 记录并回 G3 确认 |

#### S7 · 验收（QA）

| 项 | 内容 |
|---|---|
| 输入 | 任一阶段产物 + 该阶段的验收清单 |
| 输出 | Pass / Fix / Redo + 具体修改指令（点名哪一处、改成什么） |
| 负责人 | 验收官 |
| 验收 | 每条问题可执行；最多 2 轮；仍不通过交人 |
| 预算 | < ¥2 / 次，< 2 分钟 |

**验收官不是评审官。** 它只回答「做对了吗、全不全」，不回答「能不能赢」。后者是评审官（v0.2）的事。

#### S8 · 交付（Deliver）

| 项 | 内容 |
|---|---|
| 输出 | Deck + 预算表 + 自检报告 + 答辩 Q&A |
| 验收 | 客户能直接提报，不需要你再解释 |

#### S9 · 复盘（Debrief）

| 项 | 内容 |
|---|---|
| 输入 | 结果 + 客户反馈 + 评委原话 |
| 输出 | 复盘卡（3 问）+ Outcome + Playbook 更新建议 |
| 负责人 | 总导演（G6） |
| 验收 | 3 问必答；评委原话原文（不改写）；48 小时内完成 |
| 失败 | 不填 → 项目不关闭，下次检索缺数据 |

### 4.4 异常路径

| 情况 | 处理 |
|---|---|
| brief 缺失 / 矛盾 | 出反问清单，不猜；G1 不通过不进入 |
| 客户中途改需求 | 版本快照；只重跑受影响的 S3–S4；记录变更原因 |
| 时间不够 | 降级交付：1 张策略卡 + 1 页 brief 解码，明确告知 |
| 客户要「直接给 deck」 | 先给启动包（10 分钟），确认后再给 deck，避免返工 |
| 证据推翻论点 | 启动包升 v2，不重开闸门，决策日志记一条；若论点整体崩塌则回 G3 |
| 启动包被否 2 次 | 交给人工（总导演）直接口述论点，执行总监只做结构化，不再自行判断 |
| 证据找不到 | 标「待补充」，不编；在自检报告里列为风险 |
| 策略与创意冲突 | 回 G4 或 G5，由总导演裁决，记录决策日志 |

### 4.5 状态与数据

- 每次状态流转写一条 event：`project_id / from / to / actor / timestamp / note`。
- 每次产物落库带 `version`，支持回滚。
- 所有闸门决策进 `decision_log`，是复盘和规则学习的原料。
