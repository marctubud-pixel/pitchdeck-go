# 0003 · 单人优先（single-player）

- 状态：已接受
- 日期：2026-11-12

## 背景

比稿在现实里是团队运动：策略、创意、媒介、客户总监，5–8 个人。所以一个自然的问题是：这个产品该不该一开始就做多人协作？

## 决策

**v0.1–v1.0 只做单人。一个项目一个主理人。**

理由：

1. **产品自己就在消灭多人需求。** AI 替掉的是文案、创意、媒介这几个岗位。先把 5 个人压成 1 个，再去做协作，是自相矛盾。
2. **买单的是一个人。** 合伙人 / 一人公司 / 品牌经理。团队采购要过 IT、要试用、要权限，销售周期从一周变三个月。
3. **多人的成本在冲突，不在功能。** 谁能改、谁负责、版本怎么合、客户看到什么——这些问题会吃掉大量开发时间且不产生收入。
4. **北极星指标只有单人成立。** 「人时 < 6h」是一个人的账。多人进来，协调成本混入，指标失真。

## 留三扇门（现在做，成本极低）

| 现在做 | 以后能换来 |
|---|---|
| 所有产物带 `actor` / `version` / `decision_log` | 加人不用重写数据模型 |
| 角色用「执行总监 / 总导演 / 验收官」，不用「用户 A / B」 | 角色可以由多人担任，也可以一人兼 |
| 一个只读分享链接给客户 | 覆盖 90% 的「多人需求」——客户不需要账号 |

**关键判断：比稿里真正的「多人」不是同事，是你和客户。** 客户永远不登录系统，只打开一个链接。所以多人的第一层是「对外只读」，不是「对内权限」。

## 什么时候改

出现以下任一信号才重新评估，而不是「客户提了」：

- 一个客户月均 > 4 个提案，单人排不过来
- 广告公司要求策略 / 创意 / 客户总监三人进同一项目
- 开始外包，需要「他只能看这一个项目」

## 对定价的影响

单人 = **按项目 / 按月收费**，不按席位。按席位是 SaaS 逻辑（要几百个客户）；按项目是 10 个客户做到 200 万的逻辑。

## 后果

- 数据模型不建 `team` / `member` 表，只建 `actor` 字段。
- 不建权限系统，只建「本人 / 只读链接」两档。
- 对外话术统一为：「一个项目一个主理人，其他人用只读链接」。
